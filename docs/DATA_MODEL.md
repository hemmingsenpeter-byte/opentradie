# Data model

All identifiers are UUIDs. Every domain table carries `tenant_id`; composite foreign keys `(tenant_id, id)` keep related rows inside one tenant. Source of truth: `packages/database/migrations/` (do not trust this page over the SQL).

## Three kinds of data

| Kind                     | What                                                                                        | Where                                                                                         | Rule                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A. Authoritative records | Business, users, customers, properties, jobs, job timeline, quotes, approvals, rates, audit | PostgreSQL                                                                                    | Changed only by validated API services; audited                                                            |
| B. Searchable knowledge  | Communications, documents, notes, extractions, embeddings with provenance                   | PostgreSQL (`knowledge_items`, `communications`, `documents`, `job_notes`) and the file store | Retrieval preserves source, tenant scope, timestamp, confidence and verified/inferred/user-supplied status |
| C. Agent runtime state   | OpenClaw sessions, transcripts, memory                                                      | Inside the OpenClaw Gateway                                                                   | Private to OpenClaw; never read or modified directly; never a source of truth                              |

Raw LLM history is never the source of truth. Unverified AI output is never automatically converted into authoritative customer or financial records.

Hierarchy: Business, then Customers, then Properties and Jobs (a job may be at one of its customer's properties), then Quotes. Communications, notes and documents attach to a customer or a job; every job change is appended to `job_events` (`0007` adds the event types `time_recorded`, `material_added` and `communication_drafted`, extending the existing CHECK list in place).

Migration `0005` numbered existing quotes per business in creation order (`Q-0001`, …), made each its own version group, converted line quantities to thousandths (`quantity × 1000`), set line kind from the unit (hour → labour, otherwise fee), recorded owner rejections with `decision_source = 'owner'`, and stored a standard-rate tax breakdown for quotes with lines.

Migration `0007` adds the agent tool gateway tables above, and the `job_events` type list gains `time_recorded`, `material_added` and `communication_drafted` (extended in place, so types from earlier migrations are kept). `tests/integration/migrations.test.ts` asserts that the final constraint allows every type in `JOB_EVENT_TYPES` (`packages/database/src/job-events.ts`).

Migration `0009` adds scheduling. `communications.status` gains `discarded` (a reminder draft for a cancelled or moved appointment), and the `job_events` type list gains `appointment_scheduled`, `appointment_rescheduled`, `appointment_confirmed` and `appointment_cancelled` (extended in place, so types from other migrations are kept). Appointment, availability, settings and reminder rows are included in the export.

Migration `0010` (numbered after `0007`, whose time entries and materials it references) adds invoices and accounting sync. `documents` gains `invoice_id` and the kind `invoice_pdf`; `job_time_entries` and `job_materials` gain `invoice_id`; the `job_events` type list gains `invoice_drafted`, `invoice_approved`, `invoice_posted`, `invoice_sync_failed`, `invoice_voided` and `invoice_paid` (both lists extended in place).

Migration `0004` turned each distinct existing `(customer, site_address)` into a property, linked those jobs, and backfilled a `created` event per job and a `note_added` event per note.

## Export

`GET /api/export` (owner only, audited as `business.exported`) returns `opentradie-business-export` format version 1: `schemaVersion` (latest applied migration), `generatedAt`, and every tenant-scoped business table as `{columns, rows}`. It never includes `password_hash`, session tokens, `encrypted_credentials`, `encryption_key_id` or search vectors, and leaves out operational tables (sessions, idempotency records, queue, relay inbox, installation claim, embeddings, agent sessions and the agent tool call log). Document and photo bytes are not embedded; rows carry `storage_key`, `size_bytes` and `sha256`. `quote_acceptance_tokens` is exported without `token_hash`; `quote_decisions` is exported in full. Action proposals, tool policies, time entries and materials are exported, as are invoices, invoice lines, external references, sync attempts and payment snapshots; the outbox and pending OAuth sign-ins are not. An outbound message draft for a quote that is still open contains a live acceptance link.

`GET /api/customers/:id/export` (owner only, audited as `customer.exported`) returns `opentradie-customer-export` format version 1 with the same column exclusions, limited to one customer's rows (`CUSTOMER_SCOPE` in `apps/api/src/services/customer-privacy.ts`). `voice_notes` is now part of both exports. Migration `0012_customer_erasure.sql` adds `customers.erased_at` and lets the `job_events` and `quote_decisions` append-only triggers accept one UPDATE shape only: in a transaction with `opentradie.erasure = 'on'`, setting the redacted columns to fixed redaction values with every other column unchanged. `POST /api/customers/:id/erase` uses it; see [ADR 0025](adr/0025-customer-export-and-erasure.md) for what is redacted and what is retained.

## Not stored on purpose

Prompts, provider responses and message bodies in logs; plaintext credentials; OpenClaw state.

Migration `0013_mail_connections.sql` adds `gmail`, `microsoft_graph` and `fake_mail` (the MOCK mailbox) to `oauth_authorisations.provider` and `fake_mail` to `provider_connections.provider`, so mailbox connections reuse the sealed-token rows and hashed OAuth state of the Xero connection ([ADR 0026](adr/0026-shared-oauth-connection-flow.md)).

Migration `0014_collections_follow_ups.sql` adds `collections_settings` (one row per business: enabled, stage day offsets, per-stage auto-send; off and approval-required by default), invoice hold columns (`collections_hold`, `collections_hold_reason`, `collections_hold_at`) and the `escalated` reminder status; follow-ups are `reminders` rows with subject `invoice` and dedupe key `invoice:<id>:<stage>` ([ADR 0027](adr/0027-collections-follow-ups.md)).

Migration `0015_calendar_feed_tokens.sql` adds `calendar_feed_tokens` (tenant, user, SHA-256 `token_hash`, `created_at`, `revoked_at`, `last_used_at`; at most one active link per user). The table is excluded from the data export because it holds security secrets ([ADR 0019 amendment](adr/0019-scheduling-and-reminders.md)).

Migration `0016_mailbox_sync.sql` adds `provider_connections.sync_cursor` (the Gmail history id or Graph delta link the `mail.sync` task resumes from; not a credential) and `last_synced_at`, and the `mailbox_sync` value to `communications.origin`, extending the CHECK list by reading its current values ([mail](integrations/mail.md#mailbox-sync)).

Migration `0017_mail_sync_warning.sql` adds `provider_connections.sync_warning` (`cursor_reset` or NULL) and `sync_warning_at`: set when the provider expired the sync cursor and `mail.sync` restarted it from now, so the owner is told mail may have been missed ([mail](integrations/mail.md#mailbox-sync)).

Migration `0018_fake_accounting_ledger.sql` adds `fake_accounting_contacts`, `fake_accounting_invoices`, `fake_accounting_payments`, `fake_accounting_idempotency` (tenant-scoped, JSON payloads) and the sequence `fake_accounting_seq`: the fake accounting provider's ledger, so the API and a separate worker process share one mock "external system" ([ADR 0029](adr/0029-postgres-backed-fake-accounting-ledger.md)). **Demo and test only**: empty unless `ACCOUNTING_PROVIDER=fake` (refused in the cloud profile and with `NODE_ENV=production`), never read by business logic, and excluded from the data export. Backups copy it like any table.
