# Security: threat model

Scope: OPENTRADIE v0.1 (pre-release, no external audit). Vulnerability reporting: see the root [SECURITY.md](../SECURITY.md). Control status uses the labels from [ARCHITECTURE.md](ARCHITECTURE.md); statuses were reconciled against the merged code and tests on 2026-10-19. CI results are not claimed: see GitHub Actions.

## Assets

1. Customer personal data: names, phones, emails, addresses, job notes, messages.
2. Business financial data: approved rates, quotes, approvals, later invoices and accounting links.
3. Credentials: user password hashes, session tokens, provider OAuth tokens/API keys, `CREDENTIAL_ENCRYPTION_KEY`, `SESSION_SECRET`, OpenClaw Gateway token and device identity.
4. Audit trail integrity.
5. Availability of the owner's quoting workflow.

## Actors

| Actor                                      | Trust                                                                      |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| Owner                                      | Authenticated, may approve quotes                                          |
| Viewer                                     | Authenticated, read-only                                                   |
| Unauthenticated internet user              | Untrusted                                                                  |
| Customer / sender of inbound messages      | Untrusted content author                                                   |
| The language model and anything it outputs | Untrusted, manipulable                                                     |
| OpenClaw Gateway process                   | Trusted infrastructure for one business, but its model output is untrusted |
| Hosted model / embedding provider          | External third party                                                       |
| Cloud host, relay or tunnel operator       | External third party (metadata at least)                                   |
| Another business on shared infrastructure  | Untrusted; must have a separate deployment                                 |

## Trust boundaries

1. Browser to API: session cookie, CSRF defences, input validation, rate limiting.
2. API to PostgreSQL: the API holds the only database credentials. The agent never receives them.
3. API to OpenClaw Gateway: authenticated WebSocket (token plus paired device). The Gateway is a **separate process per business**. OpenClaw's trust model supports one trust boundary per Gateway and states that operator access is not per-user tenant isolation and that `sessionKey` is a routing selector, not an authorisation token. OPENTRADIE therefore: one Gateway per business installation, never shared credentials, never a shared Gateway for mutually untrusted businesses.
4. OpenClaw to model provider: governed by the Gateway's configuration and the privacy mode ([PRIVACY.md](PRIVACY.md)).
5. API and worker to accounting providers (Xero; [ADR 0023](adr/0023-invoices-outbox-and-xero-sync.md)): OAuth tokens sealed at rest and business-scoped; writes are idempotent and driven by the outbox; provider responses are untrusted and never logged. The Xero connection is implemented but has never been run against Xero. Email: Planned. Mail providers (Gmail, Microsoft Graph): adapters and OAuth connection implemented, not integration-tested (same hashed single-use state, sealed PKCE verifier and sealed tokens as Xero, [ADR 0026](adr/0026-shared-oauth-connection-flow.md)); a revoked grant marks the connection for reauthorisation and fails sends with `MAIL_REAUTHORISATION_REQUIRED`; inbound email arrives only through the signed endpoint or the owner's paste route.
6. Local machine to cloud/relay (hybrid): Planned ([RELAY.md](RELAY.md)).

## Route sweep and recovery evidence (Phase 7)

- **Route sweep** (`tests/security/route-sweep.test.ts`, Implemented and tested): every route is enumerated from the OpenAPI document and cross-checked against Fastify's own route table, with every optional route family switched on. A route Fastify serves that is neither documented nor in the explicit public allowlist fails the test, and an allowlisted route that no longer exists fails too. For every non-public route an unauthenticated request gets 401; for every mutating route a viewer gets 403 `OWNER_REQUIRED` and the route must be owner-only unless it is on the two-entry viewer list (logout, mark thread read); for every `:id` route a second runtime for tenant B, over the same database, gets 404 for real tenant A ids of each resource type (customers, jobs, properties, quotes, appointments, communications, documents, threads, invoices, proposals, voice notes), the response never contains the tenant A id, and tenant A's audit log is unchanged. Public routes: health, OpenAPI, login, public quote token routes, calendar feed, inbound email webhook (HMAC), relay (HMAC), Xero and mail OAuth callbacks, agent-tools MCP (bearer). The sweep found no failing route.
- **Worker crash recovery** (`tests/integration/recovery.test.ts`, Implemented and tested against fakes): a worker leases a task with a 1 ms lease, dies mid-task without reporting, and a healthy worker reclaims the task after the lease expires. Covered: `accounting.post_invoice` crash after the fake ledger accepted (retry links the existing record, one ledger invoice, one create call); `inbox.send` crash after the fake provider accepted (never resent, marked `SEND_OUTCOME_UNKNOWN`); collections scan crash while writing the reminder draft (one reminder, one draft after retry); outbox dispatcher crash after enqueue but before marking dispatched (one task, one ledger effect).
- **Database connection loss** (`tests/integration/database-recovery.test.ts`, Implemented and tested against real PostgreSQL): an admin connection runs `pg_terminate_backend` on every backend of the test database. `/health` returns 200 again within seconds and an authenticated, idempotent customer create succeeds with its audit event. A task whose connection is killed mid-run (a `pg_sleep` the termination interrupts) is retried by the shared worker loop (`runWorkerLoop`, `packages/platform/src/worker-loop.ts`) and completes on attempt 2 with exactly one effect and one recorded failure. With `ALLOW_CONNECTIONS false` plus termination, `/health` returns 503 with `database.status` not ok and the worker loop keeps running; after connections are re-allowed, `/health`, a new task and a mutation all succeed. Bug found and fixed: the standalone worker (`apps/worker`) had no error handling around its loop, so one transient database error (connection terminated or refused) rejected `main()` and exited the process; it now shares the API's catch-and-retry loop. Not covered: a real PostgreSQL server restart or failover (the test terminates backends of one database on a running server).
- **No hosted fallback** (`tests/portability/no-hosted-fallback.test.ts`, Implemented and tested): agent, triage, embeddings and speech each refuse hosted and unverified destinations under `LOCAL_ONLY` and under `APPROVAL_REQUIRED` without an approval (the hybrid profile's default), and no provider is called.

## Agent restrictions

The agent must never get: shell, arbitrary filesystem, production database credentials, cross-customer retrieval, or general send/financial authority. Configure the Gateway with tools denied and a dedicated agent ([OPENCLAW_INTEGRATION.md](OPENCLAW_INTEGRATION.md)); verify with the installed version's own security-audit tooling, because config keys and defaults change between OpenClaw releases. OpenClaw's documented defaults are permissive for a trusted single operator (for example host exec without prompts and session visibility `all`), which is why a dedicated, locked-down Gateway is required here.

## Residual risks

- The language model can still produce a plausible but wrong proposal; the owner is the control.
- The API cannot verify the Gateway's real model configuration or tool policy; a misconfigured Gateway undermines `LOCAL_ONLY`.
- No multi-factor authentication, account recovery, or per-user audit review UI in v0.1.
- Single owner account model; no fine-grained roles beyond owner/viewer.
- Rate limiting is per process; no WAF; TLS and DDoS protection are the host's job in cloud.
- The relay ingress (`POST /relay/v1/events`, HMAC-SHA256 with a 5 minute freshness window) is built and tested, but there is no public multi-customer relay; the shared secret is the only credential, and the sources it accepts are mock/test sources.
- The Xero OAuth exchange, token refresh and posting have never been run against Xero; the behaviour of Xero's idempotency keys (retention, reuse with a different payload) is unverified, which is why the stored reference and `Reference` lookup come first.
- The fake accounting adapter keeps its mock ledger in the API process; with `RUN_WORKER=false` and a separate worker the two would disagree. It is for demos and CI only.
- No penetration test or third-party review has been done.
