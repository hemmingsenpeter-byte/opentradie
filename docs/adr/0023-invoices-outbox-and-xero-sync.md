# ADR 0023: Invoices, the transactional outbox and Xero sync

- Status: Accepted; implemented and tested with the fake accounting adapter. The Xero path is implemented, not integration-tested.
- Date: 2026-10-20
- Builds on: [ADR 0012](0012-durable-workflow-outbox-on-existing-queue.md) (outbox on the existing queue), [ADR 0013](0013-accounting-adapter-xero-ledger-authority.md) (ledger authority), [ADR 0020](0020-accounting-adapter-contract.md) (adapter contract), [ADR 0016](0016-fractional-quantities-gst-engine-pdf-documents.md) (pricing, GST, TSI, PDFs), [ADR 0021](0021-agent-business-tool-gateway.md) (agent tools)

## Context

Features 3 (invoice from a job), 4 (Xero) and the foundation of 15 (`invoice.prepare`) need: invoices built only from owner-approved prices, no double billing, an owner approval gated by New Zealand taxable supply information (TSI), and a push to the ledger that survives crashes and retries without creating duplicates. The adapter contract, Xero adapter, fake adapter, credential envelope and in-memory stores already existed (ADR 0020) but had no persistence, routes or worker jobs.

## Decision

1. **Migration `0010_invoices_accounting.sql`.** ADR 0012 reserved `0006` for this work, but invoices reference `job_time_entries` and `job_materials` from `0007`, and a migration must sort after every table it references. `0010` is therefore used; `0006` stays unused. Tables: `invoices`, `invoice_lines` (same pricing CHECKs as quote lines plus their source), `external_references`, `oauth_authorisations`, `event_outbox` (ADR 0012's `outbox_events`), `accounting_sync_attempts` (ADR 0012's `sync_attempts`) and `payment_snapshots`; `invoice_id` columns on time entries, materials and documents; per-business `next_invoice_number`, `payment_terms_days` and `accounting_sales_account_code`.
2. **Invoice content is deterministic.** A draft is created only for a `completed` job, from the accepted quote (lines copied as accepted, with the quote's tax settings), and/or uninvoiced time entries priced from the owner-approved rate each references, and materials at recorded cost times owner-approved markup. Unpriced materials are left out and reported. Clients and agents never send amounts; owner edits keep a line's price source or add lines from approved rates, cost plus markup or an owner-entered price.
3. **No double billing.** A time entry or material is claimed by setting its `invoice_id` under a row lock, only from unclaimed rows; dropping a line or voiding a draft releases it. An accepted quote can be on at most one live invoice (partial unique index).
4. **Approval.** The owner approves a draft; the core TSI check must report nothing missing (the API returns `INVOICE_INCOMPLETE` with the explicit list). Approval renders the invoice PDF with `renderInvoicePdf`, stores it as a document, and writes the `accounting.post_invoice` outbox event in the same transaction. An approved invoice is not edited in OPENTRADIE; corrections happen in the ledger (credit note), and only drafts can be voided here.
5. **Outbox dispatch.** `dispatchOutbox` (run by the in-process and standalone worker loops) copies undispatched rows into `scheduled_tasks` with `outbox:<id>` as the task idempotency key, claiming rows with `FOR UPDATE SKIP LOCKED`. A crash between enqueue and marking a row dispatched yields one task, not two.
6. **Posting.** The handler takes a per-invoice advisory lock, then: if the invoice is no longer `approved`/`posting` it does nothing (redelivery is a no-op); otherwise it looks for an existing ledger invoice by the stored external reference, then by the provider `Reference` (our invoice number), and only then calls `AccountingSyncService.pushDraftInvoice` with the idempotency key derived from `(tenant, invoice id, version)`. This covers a crash after the provider created the invoice but before our commit, even if the provider has forgotten the idempotency key. Lines with a percentage discount are sent as one unit at the discounted amount, so ledger lines equal ours; negative discount lines are refused (`unsupported`) until the contract supports them.
7. **Failure handling.** `AuthExpired`: refresh once and retry with the same keys. `ReauthorisationRequired` (or a second expiry): connection marked `error`, tokens discarded, invoice `sync_failed` with `reauthorisation_required`. `RateLimited`: the task is rescheduled after the provider's `Retry-After` (new `RetryLaterTaskError` in the queue). `Transient`: queue backoff, `sync_failed` (`transient_exhausted`) on the last attempt. `Validation`, `Conflict`, `Permanent`: `sync_failed` with our message and the provider's issues, which are shown to the owner and never logged. The owner can retry; the provider idempotency key is unchanged.
8. **Reconciliation.** `accounting.reconcile` reads each posted or part-paid invoice from the ledger into `payment_snapshots` and moves the invoice to `part_paid` or `paid`. It runs as a chain of hourly tasks (one per hour bucket) while anything is open, and on demand from `POST /api/accounting/sync`. Ledger figures are stored, never recomputed. No payment reminders exist yet.
9. **Connections.** PostgreSQL `ConnectionStore` and `ExternalReferenceStore` implement the ADR 0020 interfaces. Token refresh runs under `SELECT ... FOR UPDATE` on the connection row (`TokenStore.refreshExclusive`): a second worker waiting on the lock re-reads and uses the already rotated tokens instead of spending the single-use refresh token again. OAuth `state` is stored as a SHA-256 hash and the PKCE verifier sealed with the credential envelope; both expire after 10 minutes and are single-use. The callback is a public route because the `SameSite=Strict` session cookie is not sent on the provider's cross-site redirect; the stored state binds it to the owner who started it.
10. **Configuration.** `ACCOUNTING_PROVIDER=none|xero|fake` (default `none`). `xero` needs `XERO_CLIENT_ID`, `XERO_CLIENT_SECRET`, `XERO_REDIRECT_URI` (HTTPS, or HTTP on loopback, ending `/api/integrations/xero/callback`) and `CREDENTIAL_ENCRYPTION_KEY` (with optional `CREDENTIAL_ENCRYPTION_KEY_ID` and `CREDENTIAL_ENCRYPTION_RETIRED_KEYS`). `fake` is a mock: it also needs `ACCOUNTING_ALLOW_FAKE=true`, and is refused in the cloud profile and with `NODE_ENV=production`. The UI labels it as a mock. One accounting runtime is built per process and shared by the API and the in-process worker, because the fake adapter's ledger lives in memory.
11. **Agent tools.** `invoice.prepare` now executes, after owner approval of the proposal, through the same `createInvoiceFromJob` service and produces a draft that still needs its own approval; its input has no amount fields. `payment.status` returns invoice status and the last reconciled paid and due amounts.

## Consequences

- Invoices, outbox posting and reconciliation are Implemented and tested against real PostgreSQL with the fake adapter (`tests/integration/invoices-accounting.test.ts`, `tests/e2e/invoicing.spec.ts`). That is not evidence that Xero works: the live verification steps in [docs/integrations/accounting.md](../integrations/accounting.md) have not been run.
- Xero rounds GST per line while OPENTRADIE rounds per tax-code group; a one-cent difference is shown to the owner as a warning, and the ledger's figure is authoritative.
- Changing settings that alter the posted payload (for example the sales account code) after a failed post and then retrying reuses the same idempotency key; the stored reference and `Reference` lookup still prevent duplicates, but the provider's behaviour on key reuse with a different payload is unverified.
- A standalone worker with `RUN_WORKER=false` on the API cannot be combined with the fake adapter (two separate mock ledgers).
